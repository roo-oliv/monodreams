# level-editor — overview

The in-game level editor: an always-on editor shell over the real game pipeline, driven by a **transport** (Play/Pause/Restart). The editor is not a separate application or renderer — it is the running game under the `--editor` run configuration (see `docs/CORE_TENETS.md`, "The editor is part of the game"). While the transport is **Paused** (`RunMode.Edit`) the same world, the same `Camera`, and the same `CullingSystem → SpritePrepSystem → YSortSystem → MasterRenderSystem` draw stack the player sees stay live; game logic, physics, and camera-follow freeze; and editor tooling (selection, gizmos, undo, scene save/load, toolbar) runs on top. Pressing **Play** runs the game inside the inset viewport with the shell still up; **Restart** rebuilds the scene from the original load (discarding unsaved edits).

## Purpose

A game built on MonoDreams should be editable *inside the running game*, previewing exactly what the player sees rather than approximating it in a bespoke editor renderer. The editor achieves this by gating the game pipeline on an engine-wide run state instead of forking it: each game system is wrapped (opt-in) in a `GatedSystem` carrying an `EditTimeBehavior` policy, and flipping `GameState.RunMode` from `Play` to `Edit` enters/exits editing with no screen swap, preserving all in-world state.

## What ships

### Run-state foundation (ships in `foundation`, Wave 1)

The editor's cornerstone is not in this module — it is in `foundation`, because every screen (editor or not) must understand it:

- `RunMode` enum (`Play` / `Edit`) + `GameState.RunMode` property (default `Play`).
- `EditTimeBehavior` enum (`RunNormally` / `Freeze` / `RunPartial` / `RuntimeEditable`).
- `GatedSystem` — an `ISystem<GameState>` decorator that wraps a child system + a policy and runs the child only when the run mode admits it.

See `MonoDreams/foundation/docs/premises.md` ("Edit-time behavior is a per-system policy honored by `GatedSystem`" and "Default `RunMode = Play` preserves all existing pipelines").

### Serialization (Wave 2, live — under `Serialization/`)

The scene-persistence substrate. It is infrastructure (services), not components — ECS purity keeps components pure data and puts the read/write behaviour in the registry/serializers.

- `SceneData` / `SceneEntityData` / `SceneCameraData` / `SceneLayerData` — the in-memory model of a native scene (1:1 with `scene-format.md`): `version` (now `3`, camera-as-entity — CM), `layers[]`, a reserved `sources[]`, and `entities[]` (each a `components{}` map + an optional `parent` index). The camera is an ordinary `core.Camera` ENTITY in `entities[]` now; `SceneCameraData` (the old top-level `camera` block) survives ONLY as a deserialization-only DETECTION target — `SceneVersionGuard` refuses a legacy file carrying it (run `monodreams migrate`), and `CameraMigration` lifts it into a camera entity. The writer never emits it.
- `ComponentSerializer` — a `(write, read)` pair for one component `Type`, keyed by a stable string.
- `ComponentSerializerRegistry` — the opt-in registry (`Type` → serializer). Discovers every component on an entity via DefaultEcs `ReadAllComponents`, writes the registered ones, and emits a `Logger.Warning` for any unregistered one (skip, never silent drop). Loading an unregistered component key throws (fail loud).
- `EngineComponentSerializers.RegisterEngineComponents` — registers the engine's serializers (`Transform`, `SpriteInfo`, `EntityInfo`, the colliders, `RigidBody`, `Velocity`, the `ChildOf` parent link). Centralized here because this module already depends on the modules those components live in.
- `SceneSerializer` — the in-memory round-trip seam: serializes a set of entities to `SceneData` (preserving the `ChildOf` parent graph as indices) and reconstructs them in two passes (create + deserialize, then wire parents). Wave 3 layers JSON file I/O + `LoadSceneRequest` + `Texture2D` rehydration on top.
- `GameProject` (project-persistence PS2, live) — the `game.mdproj` project manifest (`formatVersion`, `startScene`, `levelsDir` default `Levels`, `assetRoots`), read/written through the SAME `CanonicalJson` policy scenes use so it is byte-stable + diffable (`assetRoots` preserves authored order). It makes "a MonoDreams game" a versionable unit: the editor reads it to anchor the project root, the game reads it at boot to resolve `startScene` (PS4). The example manifest ships committed at `MonoDreams.Examples.Core/Content/game.mdproj` (under `Content/` + an MGCB `/copy:` so `TitleContainer` can read it, like `blender_level.json`).

### Components

- `SceneObjectComponent` (Wave 3, live, under `Component/`) — a pure tag marking a **save-root** entity; the `SceneWriter` includes each tagged root plus its `ChildOfComponent` descendant closure.
- `SelectedComponent` (Wave 4a, live, under `Component/`) — a pure tag marking the currently-selected entity for the gizmo and toolbar (single-select; transient, not serialized).
- `EditorIdComponent` (Wave 4a, live, under `Component/`) — a stable monotonic id the selection system assigns to each candidate the first time it sees it; the selection-owned tiebreak for an exact-depth pick (the renderer's insertion index is private).
- `GizmoStateComponent` (Wave 4b, live, under `Component/`) — the gizmo's configuration (active `GizmoTool`, `SnapEnabled`, `GridStep`, `RotationStepRadians`) plus, since island-authoring Slice 1, the coarse **tool modality** `EditorToolMode Mode` (`SelectTransform` default / `Place`; Scatter/GroundPaint/Road reserved) — which tool family owns a viewport press: selection + gizmo act only in `SelectTransform`, the palette's placement only in `Place`. A single editor-owned entity the toolbar/palette mutate and `GizmoSystem` reads. Pure data — the per-drag accumulation is `GizmoSystem`'s private frame state.
- `GizmoOverlayComponent` (Wave 4b, live, under `Component/`) — tags the gizmo's own overlay mesh entities (the selection outline + the move/rotate/scale handles) so the system can manage them. They are standalone (never `ChildOfComponent`-parented), native-resolution chrome: screen-baked meshes on `RenderTargetID.Editor` with **no** `VisibleComponent` (the chrome rule — `MeshPrepSystem` would overwrite the identity `WorldMatrix` their screen-baked vertices require).
- `ToolbarButtonComponent` (Wave 4b, live, under `Component/`) — tags a toolbar button with its `EditorToolbarAction` + its `Bounds` for `ToolbarSystem`'s hit-test (since Wave 7: physical screen pixels, tested against the cursor's raw `ScreenPosition`).
- `GizmoProxyComponent` + `ProxyBindingKind` (Wave 8b, live, under `Component/`; **whole-shape collider kinds retired in CE-C**) — the pure-data binding of an edit-time gizmo proxy: the bound target entity, a `ProxyBindingKind`, and an `Index` for sub-element bindings. **Colliders-as-entities (CE-C): a collider is now a first-class editor entity — border-picked on its world shape and moved/scaled by the ordinary gizmo — so the whole-shape `BoxColliderBounds` / `ConvexColliderShape` proxy kinds are DELETED.** The surviving proxies are the TRANSIENT sub-element grips a real entity cannot be (standalone-overlay entities, like the camera-glyph overlay): `ProxyBindingKind.ConvexVertex` (a convex collider entity's per-vertex handles, `Index` = the vertex ordinal) and `BoundaryVertex` (a boundary polyline point) — plus the reserved slot for the road tool's spline control points (Waves D/F). The proxy entity itself is a standalone overlay (own `TransformComponent` at the grip's world position; a cyan outline mesh screen-baked on the Editor target, no `VisibleComponent`), transient and never serialized.

- `EditorInfrastructureComponent` (transport model, live, under `Component/`) — a pure tag marking every editor-owned entity (chrome, panel rows, gizmo overlays/proxies, the gizmo-state entity, the overlay-provided cursor) so the transport's Restart sweep never disposes the editor's own machinery. Set at every editor entity-creation site.

### Systems

- `SceneReaderSystem` (Wave 3, live, under `System/`; **generalized onto the game boot in PS4**) — subscribes to `LoadSceneRequest`, reads the scene JSON (content stream via `TitleContainer`, or `IPlatformServices` for host-filesystem user data), deserializes via the Wave-2 `SceneSerializer` (two-pass create + deserialize + parent-wire), rehydrates each sprite's `Texture2D` from its `AssetKey`, and fails loud on an unregistered component key. The texture loader is injectable (`Func<string, Texture2D>`) so it is unit-testable without a `GraphicsDevice`. **PS4:** it is the native reader the game boot uses too — the native-first `LevelLoadRequestSystem` publishes a `LoadSceneRequest` when a bundled `Content/Levels/<id>.mdscene` exists, so the SAME reader serves both the editor's scene reload (`LoadSceneRequest` — Save-then-reload / the Scenes-panel load; there is no Load button after UX-D) and `LoadLevelRequest(id)`; it runs in both run modes and with no editor composed (a shipped game builds a standalone one).
- `SelectionSystem` (Wave 4a, live, under `System/`; target-aware since Wave 8a) — on a left-button press in Edit, hit-tests the cursor against each rendered sprite's quad (`SpriteHitTest`, honoring rotation/scale/origin/offset) and selects the frontmost. Main-target sprites test the cursor's `WorldPosition`; UI/HUD/Scroll-target sprites test `VirtualPosition` (their transforms are virtual coordinates); the Editor target (chrome) is never a candidate. Across targets the composite order ranks (Main < UI < HUD < Scroll); within a target it is MAX final post-YSort `DrawComponent.LayerDepth`, tiebroken by `EditorIdComponent`. Ordered at the end of the draw pipeline so it reads the final depth this frame; Edit-guarded; click-empty clears — but a press the gizmo **claimed** (`GizmoStateComponent.PressClaimed`: the press landed on the active tool's handle, or a handle drag is in progress) is skipped entirely (no re-pick, no clear), so rotate/scale handles outside the sprite's bounds stay grabbable; the same-frame claim is readable because the gizmo runs in the update pipeline. A plain `ISystem` over its own candidate set (not an `AEntitySetSystem`, whose empty-set early-out would disable proxy picking in a sprite-less scene).
- `EditorCommandSystem` (Wave 4a, live, under `System/`; widened island Slice 2; collider ops retargeted in CE-C) — Edit-guarded; translates delete/undo/redo intent into `EditorHistory` operations, plus the toolbar's selection-edit actions: `BringForward`/`SendBack` (within-band SOURCE sort nudges), `AddBoxCollider`/`AddConvexCollider`, `RemoveCollider`, and `AddVertex`. **Colliders-as-entities (CE-C): `AddBoxCollider`/`AddConvexCollider` create a footprint-shaped child collider ENTITY via `CreateEntityCommand` (auto-named, passive, selected), and `RemoveCollider` (−Col) deletes the selected collider entity** — a collider is no longer a component edited through a proxy. Delete is proxy-aware (`DeleteSelection`): a convex vertex proxy deletes its vertex (keeping >= 3), and a plain entity selection (including a collider entity) builds the sub-graph-snapshotting `DeleteEntityCommand`.
- `GizmoSystem` (Wave 4b, live, under `System/`; target-aware since Wave 8a; native-resolution visuals since the HiDPI wave) — reads `SelectedComponent`, hit-tests the active handle, and on a drag opens an `EditorHistory` transaction, pushes a `TransformEditCommand` each frame (computed by the pure, space-agnostic `GizmoTransform`, applying grid-snap), and commits on release → one undo step. A Main-target selection works in world space (cursor `WorldPosition`, handle hit-tests sized by `1/Camera.Zoom`); a UI/HUD-target selection works in virtual space (cursor `VirtualPosition`, no zoom compensation). Its overlay VISUALS (outline + active-tool handle, standalone `GizmoOverlayComponent` entities) are emitted by `EmitOverlays` — invoked from the draw pipeline's `editor.overlayPrep` entry (`EditorOverlayPrepSystem`) after `editor.selection`, so they bake from the frame's FINAL camera + selection — in screen pixels on the Editor target through the pure `Transform/OverlayProjection` (sizes scale with the aspect-fit factor, never the camera zoom) and clipped to the game viewport by `Transform/OverlayMeshClip`. Inert + overlays torn down in Play. Runs before `HierarchySystem` so the edit propagates the same frame.
- `ToolbarSystem` (Wave 4b, live, under `System/`; retargeted Wave 7; transport-aware) — hit-tests the cursor's raw `ScreenPosition` (physical pixels — the chrome is native-resolution) against each `ToolbarButtonComponent.Bounds` in BOTH transport states, tints the hovered button's fill, syncs the Play/Pause button's label with the state, and hands a click's `EditorToolbarAction` + the frame's `GameState` to the overlay's dispatch. The transport buttons dispatch always; the editing buttons dispatch only while Paused and render dimmed while Playing.
- `CameraNavSystem` (post-Wave-A, live, under `System/`) — Edit-guarded camera navigation: middle-mouse **pan** (the camera moves opposite the cursor's virtual-pixel delta, scaled by `1/Zoom`, so the grabbed world point stays put), scroll-wheel **zoom** (a geometric step on `Camera.Zoom`, clamped 0.25–4.0), and the public **`FrameScene()`** method that centres + zoom-fits the camera on the AABB of all `SpriteInfoComponent` content (no content = no-op) — triggered by the `EditorShortcuts` **Home** binding or the headless `view:frame` op (UX3-E), NOT a keyboard predicate on this system. Drives `Camera.Position`/`Zoom` directly (the editor owns the camera in Edit; `CameraFollowSystem` is `Freeze`-gated). Registered **before `CursorPositionSystem`** so the camera mutation is the camera the cursor's world-pos derives from that same frame. Inert in Play.
- `ModalTransformSystem` (UX3-F, live, under `System/`) — Blender's `G`/`S`/`R` modal transforms over the selection (entered from the `EditorShortcuts` table): the mouse drives grab/scale/rotate WITHOUT a button held through the SAME coalescing `EditorHistory` transaction a gizmo drag uses (one session = one undo step), with X/Y axis locks and a numeric-entry buffer that overrides the mouse. While active it owns the pointer (consumes the cursor edges — the confirm-click never re-picks, pre-mortem #4) and the keyboard (`Modal.IsActive` ORs into `ShouldSuppressInput` + the shortcut gate; Escape cancels the modal). The camera entity composes (G moves it, S → `CameraComponent.Zoom` via `MemberEditCommand`, R rotates its Transform — legal, CM). The pure math is `Transform/ModalTransform`; `modal:*` ops drive it headlessly. Woven `editor.modal` after `editor.shortcuts`, before the tools. Inert in Play.
- `Transform/GizmoTransform` (Wave 4b, live) — the pure, GraphicsDevice-free transform math behind the gizmo (move/rotate/scale + grid-snap, honoring Origin); separated from `GizmoSystem` so it is directly unit-testable. Its `SpriteWorldQuad` corner helper is reused by `CameraNavSystem`'s frame-scene to compute the content AABB.
- `Navigation/CameraNav` (post-Wave-A, live) — the pure, world-free math behind `CameraNavSystem` (pan sign + zoom-clamp + content-AABB centre/fit); separated from the system so it is directly unit-testable without a real `Camera` or cursor (mirrors the `GizmoTransform` split).
- `UI/EditorChromeLayout` (Wave 7, live; UX3-F added the status bar) — the pure, world-free layout math of the shell (panel rectangles, toolbar button row, the `ViewportInset` margins, and the UX3-F `StatusBar` strip) in physical screen pixels; the same numbers feed both the chrome entities and `ViewportManager.SetViewportInset`, so the panels always exactly cover the reserved margins. The bottom inset is the assets shelf PLUS the status bar (one inset source).
- `UI/StatusBarModel` (UX3-F, live) — the pure formatter for the window status bar: the modal readout (`LeftModal`) / contextual status (`LeftStatus`) on the left, the scene id + view mode (`Right`) on the right. ASCII-only (the chrome font lacks Δ/×/°/·/●); the dirty dot is a mesh, not a glyph.
- `UI/EditorChromeBuilder` (Wave 7, live; replaces the Wave-4b `EditorToolbarBuilder`) — builds the native-resolution chrome on `RenderTargetID.Editor`: opaque panel backgrounds (fill-only `SimpleButtonComponent` meshes) + the toolbar's labelled buttons (each tagged `ToolbarButtonComponent`), with `Relayout(w,h)` recomputing everything on window resize. Labels are the screen's 48px BitmapFont at 1/3 scale (≈16 points; × the device-pixel ratio on a HiDPI backbuffer — e.g. 32 device px at DPR 2, same physical size, double the density), rendered directly at native res; `Relayout(w,h,scale)` scales every point metric by the DPR so the chrome keeps its physical size. Chrome entities carry **no `VisibleComponent`** (it would pull the meshes into `MeshPrepSystem`, which overwrites the identity `WorldMatrix` their absolute-pixel vertices require). No ImGui; web-capable.
- `System/EditorShellSystem` (Wave 7, live; constant since the transport model) — keeps the shell applied while the editor is composed, in BOTH transport states: the viewport inset, chrome relayout on window resize, and the pointer (OS cursor visible, game cursor sprite hidden). Its `Dispose` clears the inset + re-hides the OS cursor so a screen swap never leaks the shell.
- `System/EditorStatusBarSystem` (UX3-F, live) — the window status bar (`editor.statusBar`): a thin strip flush with the window bottom (part of the ONE inset, below the assets shelf), pooled labels on the `Editor` target — the live modal readout / contextual selection status on the left, the scene id + view mode + a `Warning` dirty-dot mesh on the right, all formatted by the pure `UI/StatusBarModel`. Live in both transport states.
- `System/EditorChromeRenderSystem` (Wave 7, live) — the chrome's render pass: a screen-space `MasterRenderSystem` over `RenderTargetID.Editor` into a native window-resolution target recreated on resize; always on while the editor is composed (both transport states) — only disabling the system (e.g. from the panel) nulls `CurrentTarget` and makes the `RenderLayer.Native` final-draw layer skip.
- `System/EditorPanelSystem` + `UI/SystemsPanelLayout` + the pure `UI/EditorPanelModel` (Wave 8a as the systems panel; **UX2-B** parameterized it by an `EditorPanelRole` into TWO instances — the **left tabbed panel** `Entities` / `Systems` / `Scenes` (`EditorPanelModel.Build`) and the **dedicated right Inspector** (`EditorPanelModel.BuildInspector`) — sharing one `Component/EditorPanelStateComponent` (ECS purity) and the same pooled-row machinery). Each region owns a header band (the left = its tab bar, the right = a slim "Inspector" title); the flat row lists are assembled purely (unit-testable, no world/GraphicsDevice). Because the content is dynamic, the system **pools** its row visuals over the visible window (bounded entity count) instead of one entity per row. Selection is two-way ACROSS the panels (a left-tree click binds the right Inspector).
  - **Systems** — renders the `EditorPipelineRegistrar` **tree** of both bound pipelines (update, then draw, flattened pre-order — a group row above its children, indented by `Depth`; child rows show their `LocalName` + the policy tag only when it differs from the group's) as name + policy tag + a checkbox reflecting the live enabled state. Leaf checkboxes are two-state; a group checkbox is **tri-state** (all/none/mixed, the mixed state a dark **minus bar** — the Gmail/Material mark). A row **body** click toggles via `SetEnabled` with the Gmail convention (checked/indeterminate → all off; unchecked → all on; the panel refuses to disable its own entry or any ancestor group of it); a group row's **disclosure arrow** click collapses/expands its children (the deferred follow-up, now live).
  - **Scene** — the world's entities as a **tree** (`Inspector/EntitySceneTree.Build`: roots first, `ChildOfComponent` descendants indented; **editor-infrastructure entities hidden**). Each row is labelled by its `EntityInfoComponent` name (else type, else a stable panel id) and is **selectable both ways**: a click sets `SelectedComponent` (the same tag `SelectionSystem` sets from a viewport click — the panel's chrome click is `OutsideViewport`, so neither clobbers the other), and the selected entity is highlighted. A parent row's arrow collapses its subtree.
  - **Inspector** — bound to the current selection: lists the entity's **attached components** (`Inspector/ComponentInspector.Inspect` over DefaultEcs `ReadAllComponents`) and expands each (on demand) to its **member values** (read-only `name: value` rows reflected from public fields/properties, culture-invariant floats, guarded so an arbitrary component never throws).
  - Native-pixel chrome (no `VisibleComponent`, `ScreenPosition` hit-test) laid out by the pure `SystemsPanelLayout`; wheel-scrolls whole lines; binds the Systems section lazily via `EditorOverlay.BindPipelines`; headless-drivable through the overlay's `panel:systems|scene|inspector|group <name>|inspect <type>|select <name>` ops.
- `System/ProxySyncSystem` + `Proxy/ProxyGeometry` (Wave 8b, live; registrar entry `editor.proxySync`, woven right after `editor.gizmo`; **narrowed to vertex grips in CE-C**) — under colliders-as-entities a collider is its own entity (border-picked on its world shape by `SelectionSystem`, moved/scaled by the ordinary gizmo), so the WHOLE-SHAPE collider proxies are gone. `ProxySyncSystem` now materializes only the TRANSIENT sub-element grips a real entity cannot be: a selected CONVEX collider entity's per-vertex handles (`ProxyBindingKind.ConvexVertex`, retargeted at the collider entity's own `ModelVertices`) and the boundary polyline's vertex handles — one standalone proxy per grip (a cyan outline screen-baked on the Editor target by `EmitOverlays` via the `editor.overlayPrep` draw entry, fit-scaled stroke, viewport-clipped), re-derived every frame, despawned on deselect / mode exit / target death. It also refreshes the selected convex collider entity's `WorldVertices` per frame (physics is frozen in Edit) so the `ColliderDebugSystem` outline stays coherent. `ProxyGeometry` remains the pure single source of truth for the derivations (convex world vertices mirroring `UpdateWorldVertices`, border distance for the pick, world→model delta inversion) shared by the sync, the collider-entity border pick, and the vertex write-back.
- `System/PalettePlacementSystem` + `UI/PaletteLayout` (island-authoring Slice 1, live; **cards + per-asset band marks in FW3**; registrar entry `editor.palette`, woven right after `cursorPosition` so the ghost follows this frame's cursor) — the asset palette in the shell's bottom strip (band-selector header + a wheel-scrolled grid of catalog-entry **cards** — a lazily-loaded art thumbnail on top, a truncated text label on the bottom, and a band-chip badge in the icon corner; native-pixel chrome, `ScreenPosition` hit-test, no `VisibleComponent`/`ToolbarButtonComponent`) plus the placement loop: click a card's **body** to **arm** (`Mode = Place`; the transform gizmo visibly deactivates), a tinted **ghost** preview follows the snap-quantized cursor world position (hidden over chrome; editor infrastructure, never `SceneObjectComponent`), a viewport click **places** through one snapshotting `CreateEntityCommand` (one undo step, auto-selected, keeps placing until disarmed), Escape / right-click / a transform-tool button **disarm**. The card's **band chip** cycles the asset's permanent band mark (`CycleAssetBand`); placement resolves the band as **the marked band if set, else the global selector** (`ResolveBand`). Edit-guarded (inert + ghostless while Playing; the armed item is kept). Headless-drivable via the overlay's named dispatch (`palette:<id>`, `palette:none`, `band:<name>`, `asset-band:<id>:<band>`). Placed while Paused, previewed by the REAL pipeline — the ghost and the placed prop render through the same cull/prep/Y-sort/draw stack the player sees.

### Assets (island-authoring Slice 1, live — under `Assets/`)

- `AssetCatalog` / `AssetCatalogEntry` — the drop-folder scan (`Content/Island/`, gitignored; committed `MANIFEST.md`): one entry per PNG, recursive, plus one entry per named region of a `*.slices.json` sidecar (a sliced sheet contributes regions only). The scan reads only the directory + sidecars — textures are never opened at scan. Deterministic folder-then-label order; lookup by id or full `file:` key.
- `FileAssetKey` — the `file:` AssetKey scheme (`"file:Island/props/tree01.png"`, optional `#region` suffix identifying the catalog entry; loading always opens the base PNG — the region's `Source` rect is serialized on the sprite). Graduation path: when art finalizes, assets move into MGCB content and `file:` keys flip to content keys (mechanical, greppable).
- `FileAssetTextureLoader` — lazy, memoized-per-PNG texture loads over `TitleContainer.OpenStream` + `Texture2D.FromStream`; a missing/undecodable file logs a loud warning and returns the shared **magenta placeholder** texture (never an invisible sprite). Injectable stream/decode/placeholder functions (unit-testable without a `GraphicsDevice`). Always composed by the overlay — `SceneReaderSystem` rehydrates `file:` keys through it whether or not the screen shows a palette.
- `PaletteBand` — one screen-supplied layer band (name + SOURCE `LayerDepth` + `YSorted`): the screen builds the band list from ITS `DrawLayerMap` (the module never references a game layer enum).
- `AssetBandConfig` (FW3) — the **per-asset band marks**: an `asset-bands.json` at the catalog's scan root mapping an entry id → a band name, written/read through `CanonicalJson` (byte-stable). Marks are dev-authoring metadata (they live with the gitignored packs, never in a scene file) and **survive an editor restart**. A placement resolves its band as the marked band if set, else the global selector (`PalettePlacementSystem.ResolveBand`). A rootless (test) config keeps marks in memory only.
- `SpritePropFactory` — the generic prop builder: catalog entry + band + position (+ nullable texture) → the standard renderable stack (`EntityInfoComponent`, `TransformComponent`, `SpriteInfoComponent` with the `file:` key + SOURCE sort fields, `DrawComponent`). On a Y-sorted band it applies the **feet-origin convention** (Origin = bottom-center in source pixels, `YSortOffset = 0` — the Position IS where the prop stands). `VisibleComponent` is culling-owned and `SceneObjectComponent` is the create-command's to set — the factory sets neither.

### Undo (Wave 4a, live — under `Undo/`)

- `IEditorCommand` — a reversible editor mutation as DATA + an `Apply`/`Revert` pair (ECS purity: not a behavior-laden OO object).
- `EditorHistory` — bounded undo/redo (configurable cap, oldest-evicted FIFO; empty-stack no-op) with the drag-coalescing transaction API (`BeginTransaction`/`CommitTransaction`/`CancelTransaction` → one entry per drag).
- `CompositeCommand` — bundles a coalesced transaction's commands into one undo step.
- `CreateEntityCommand` / `DeleteEntityCommand` — create tags the new root `SceneObjectComponent` + snapshots its sub-graph; delete snapshots the disposed sub-graph (reusing `SceneSerializer`) so undo restores it whole. `EntitySubgraph.Collect` is the shared `ChildOf` descendant-closure walk.
- `TransformEditCommand` — a before/after transform edit; `GizmoSystem` (Wave 4b) constructs it via `FromCurrent` each drag frame and the coalescing transaction collapses the drag into one entry.
- `ColliderEditCommand` (Wave 8b; **narrowed to convex vertices in CE-C**) — a before/after edit of a CONVEX collider entity's `ModelVertices` (the `ForConvex` factory), targeting the collider ENTITY; the write refreshes `WorldVertices` + `BroadPhaseAABB` (physics is frozen in Edit). Pushed per vertex-drag frame inside the coalescing transaction, like `TransformEditCommand`. **`ForBox` is deleted** — a box collider entity is moved/scaled by the ordinary gizmo through `TransformEditCommand` (its `Size` scales via the entity's Transform; there is no box-resize command).

### Serialization writer (Wave 3, live — under `Serialization/`)

- `SceneWriter` — computes the membership closure (`SceneWriter.CollectMembership`: every `SceneObjectComponent` root + each one's `ChildOfComponent` descendants), serializes it through the Wave-2 `SceneSerializer` into a `SceneData` (attaching `Camera` state + the `DrawLayerMap` banding), canonical-serializes it (`CanonicalJson`), and (project-persistence PS3) **writes it into the project SOURCE tree** at `ProjectRoot/LevelsDir/<sceneId>.mdscene` via `IPlatformServices.WriteAllText` (git-visible; the levels dir is created if missing). `Save(world, filePath, camera, layers)` refuses a null/empty path (defense-in-depth: nowhere to write) and returns the path written (a `Save(SceneData, filePath)` overload writes an already-built scene, the seam the editor uses to lint before writing). This retired the pre-PS3 `ExportScene`→`BaseDirectory` write, so no scene lands in `bin/…` on desktop. Save-time only — never per frame. **PS6:** on Save the overlay also (a) appends the MGCB `/copy:` entry for a **new** level to `Content.mgcb` via `MgcbLevelBundle` (zero-touch bundling — idempotent; MGCB has no glob) and (b) runs `SceneLint` and logs a **ship-readiness warning** when the scene still carries `file:` AssetKeys.
- `SceneLint` (project-persistence PS6, live, under `Serialization/`) — the pure ship-readiness analyzer: `IsShipReady(scene)` / `FindFileAssetKeys(scene)` report `file:` AssetKeys (a scene is fully portable only with **zero** of them — all graduated to MGCB content keys). Used as the Save-time warning, a committed-scenes ship-clean test, and a plain predicate.
- `MgcbLevelBundle` (project-persistence PS6, live, under `Serialization/`) — the pure zero-touch bundling helper: `EnsureCopyEntry(mgcbText, sceneId, out changed)` appends an MGCB `/copy:./Levels/<id>.mdscene` block if absent (idempotent, whole-line match). The editor calls it on Save (desktop-only file IO) so a new level bundles to the title on the next build with no manual `.mgcb` edit; a build-time `Content.npl` regen was rejected (it sweeps the gitignored placeholder-art pack into MGCB) and a raw-copy `.targets` can't reach the web `wwwroot`.

### Headless editor-op channel (Wave 5, live — under `Channel/`)

- `EditorOpPlan` / `EditorOp` — a scripted plan of editor operations (`MoveCursor` / `LeftDown` / `LeftUp` / the transport ops `Play` / `Pause` / `Restart` / `ToolbarAction`, each on a frame index) the test analogue of `InputReplayPlan` (which scripts keyboard edges). `EditorOpPlan.TryLoad` reads `editor_op_plan.json` from the debug dir (mirrors `InputReplayPlan.TryLoad`).
- `EditorOpReplaySystem` — consumes the plan and, with **no real mouse**, injects `CursorInputComponent` state (world/virtual position + the left-button press/release edges) onto the cursor, drives the transport (play/pause/restart through the bound `EditorTransport`), and fires toolbar actions through a dispatch callback. It **holds the session open** (requests exit only after the op queue drains + a tail) so the input-replay auto-exit-on-drain can't kill the editor-op run early. Registered only when a plan is present (zero cost in a normal Play run). Pairs with `CursorInputSystem.SkipHardwareRead` (the per-frame hardware read is skipped so the injected cursor survives).

### Messages

- `LoadSceneRequest` (Wave 3, live, under `Message/`) — loads a native MonoDreams scene file; distinct from `LoadLevelRequest` so it never triggers the LDtk `Content.Load` / `Remove<CurrentLevelComponent>` path. Carries the scene `Path` and a `FromContent` flag (content asset vs. host-filesystem user data).

### Composition (Wave 6, live — under `Composition/`)

The reusable seam that turns any screen into an editor-capable screen:

- `EditorPipelineRegistrar` — the pipeline **composition seam**: a screen registers each pipeline entry (`Add(name, system, policy, enabledInEditByDefault?)` for single systems; `AddGroup(name, policy, children, kind?, runner?)` for composite blocks — the registrar builds the `SequentialSystem`/`ParallelSystem` itself over NAMED, auto-prefixed children (`logic.movement`), arbitrarily nested, wrapped in ONE gate carrying the group policy, so screens never pre-build opaque composites the panel cannot see into), every entry is wrapped in a `GatedSystem` per its declared policy, and `Build()` produces the final `SequentialSystem<GameState>` over the roots. The registrar **retains** the entry tree at runtime (`Entries` flattened pre-order with `Depth`, `Roots`, `SetEnabled(name, bool)` — on a leaf, a master toggle that stops that system in BOTH modes; on a group, a cascade over its descendant leaves — plus `GetEnabledState` for the derived On/Mixed/Off tri-state and `GetEntry`) — the seam the systems panel binds to. The edit-mode default is declared at the registration site, never by an interface on the system type (the same engine system may need different policies in different games); an `enabledInEditByDefault` that contradicts the policy throws until the runtime per-mode policy override lands (a documented systems-panel follow-up).
- `EditorOverlay` — everything a screen needs to become editor-capable, built over the screen's own world/camera/layers: the shared `ComponentSerializerRegistry` + `SceneSerializer` + bounded `EditorHistory` + the `EditorTransport` + the single gizmo-state entity; every editor system (`SceneReader`, `EditorCommands`, `Gizmo`, `ToolbarMeshPrep` + `ToolbarClicks` — the two children of the `editor.toolbar` registrar group — `CameraNav`, `Shell`, the draw-side `Selection` + `ChromeRender`, and the plan-gated `EditorOpDriver`); the native-resolution chrome entities (`Chrome`) + the `ChromeLayer` final-draw layer; and the toolbar dispatch wired to those same shared instances. The overlay exposes the systems as individual hooks (they interleave with the game pipeline at documented points — see the class doc) and receives the screen's registrars via `BindPipelines` so editor tooling can enumerate/toggle the live pipeline.
- `EditorTransport` (transport model, live) — the one owner of `GameState.RunMode` under the run flag: `Play`/`Pause`/`TogglePlayPause` (Paused = Edit, Playing = Play — the shell stays composed in both) and `Restart` (clear the history, remove `CurrentLevelComponent`/`CurrentBackgroundColorComponent`, dispose every scene entity — `EditorInfrastructureComponent`-tagged entities, the cursor pipeline, and the screen's `KeepAlive`-named sub-graphs survive — then re-run the screen-recorded `Reload`; lands Paused; unsaved edits DISCARDED). The screen registers `Transport.Reload` (and optionally `Transport.KeepAlive`) in its `Load`, once it knows what it loaded; without a `Reload`, Restart is a loud no-op.
- `EditorInputBindings` — the game-specific input surface, now only the **tool-contextual** just-pressed predicates over `GameState` (cancel, order fwd/back, boundary commit, palette ghost-rotate cw/ccw); the GLOBAL editor shortcuts (Delete/undo/redo/frame/Add, plus the UX3-F G/S/R modal transforms) are the `EditorShortcuts` chord table read off the raw keyboard, NOT this surface. Keeps the overlay and every editor system free of any game input enum.
- `DefaultEditorKeys` (post-Wave-8b, live; UX3-E-updated) — the editor's default keyboard surface for hosts **without** their own keyboard-action mapping layer (the Demos host; any new host): one `AKeyboardInputHandlingSystem` over the **tool-contextual** editor keys — PageUp/PageDown (order nudge), Enter (boundary commit), Q/E (palette ghost-rotate) — exposing ready-made `Bindings` (an `EditorInputBindings`) backed by its own per-action edge states. **The global shortcuts moved to the `EditorShortcuts` chord table (UX3-E):** Delete / Home (frame) / `Cmd/Ctrl+Z` undo / `Cmd/Ctrl+Shift+Z` redo / `Shift+A` add / `G`·`S`·`R` modal transforms are read off the raw keyboard by `EditorShortcutSystem`, so this surface no longer maps them (and the bare `Z`/`Y` undo/redo were removed). Weave it as the `editor.keys` registrar entry before the editor systems that read it. A host that already maps actions (the Examples `InputMappingSystem`) keeps wiring its own action states instead. There is no mode-toggle key — play/pause/restart are toolbar transport buttons.
- `EditorRunFlag` — the editor run configuration and the ONLY door into the editor: `--editor` launch arg or `MONODREAMS_EDITOR=1` env var (pure `IsEnabled(args, getEnv)` parse + `InitialRunMode`). When active the host composes the overlay into every screen and boots the transport Paused (`ScreenController.State.RunMode = Edit`); the editor is then always visible and the transport buttons drive the game. **Rider:** add `--editor` to Program arguments, or `MONODREAMS_EDITOR=1` to Environment variables, of the `MonoDreams.Examples.Desktop` run configuration.
- `EditorProjectContext` (project-persistence PS2, live) — the resolved project root + `GameProject` manifest, computed once at editor init (desktop-only) via `Resolve`: PRIMARY the env var `MONODREAMS_PROJECT_ROOT`, FALLBACK a bounded walk-up from `BaseDirectory` to a `game.mdproj`, else `Resolved = false` (never throws). `ProjectRoot` is the directory that contains the manifest (so `ProjectRoot/LevelsDir == LevelsPath`). The head resolves it where the flag is parsed and hands it to the overlay (optional ctor param, default null) so the module stays game-agnostic; environment/filesystem access is injected (wired to `PlatformServices.Current` in the no-arg overload). It gates Save (the "no project root" cause) and, resolved, its `LevelsPath` is the directory Save writes `<sceneId>.mdscene` into and Load reads it back from (PS3). **Rider:** set `MONODREAMS_PROJECT_ROOT=<path-to-your-Content-source-project>` (e.g. the absolute path to `MonoDreams.Examples.Core`, whose `Content/game.mdproj` roots the project) beside `--editor` — this is what makes Save write into the versioned git tree rather than the walk-up-resolved build-output copy.
- `NativeLevelLoader` (project-persistence PS4, live) — the native-first bridge for the **game boot**: `CreateProbe(world, contentRoot)` builds the `Func<string,bool>` handed to `LevelLoadRequestSystem` (level-loading), which per `LoadLevelRequest(id)` probes a bundled `Content/Levels/<id>.mdscene` via `TitleContainer` and, on a hit, publishes a `LoadSceneRequest` (handled by the composed `SceneReaderSystem`) and returns true — so the LDtk path is skipped. It lives here (not level-loading) so the delegate can reference `LoadSceneRequest` without inverting the module layering. `ContentRelativePath(id)` / `NativeSceneExists(root, id)` are the shared path + probe helpers.
- `ManifestBoot` (project-persistence PS4, live) — resolves the game's boot scene from the **bundled** `game.mdproj` (read via `TitleContainer`, distinct from `EditorProjectContext`'s source-tree resolution): `TryReadManifest(contentRoot)` + `ResolveStartScene(manifest, nativeExists)` returns the manifest's `startScene` only when a bundled native scene exists for it, else null so the host keeps its default boot (a not-yet-migrated `startScene` — the Examples `island` placeholder — stays back-compat until PS5). Wired in `Game1` before the menu boot.

### Prefabs (PF phase, live — under `Serialization/`, `Undo/`, `EntityFactory/`, `Composition/`)

Prefabs are **classes** placed as **LINKED instances**: a scene stores a compact `entities[]` entry with a `prefab: "<id>"` field, its own `core.Transform`, and only its **diff-based whole-component overrides** (byte-equal to the prefab root ⇒ inherited/omitted, byte-different ⇒ kept) — instance children are prefab-owned and NEVER serialized. Authoritative design: [`../../../docs/level-editor/prefab-workflow.md`](../../../docs/level-editor/prefab-workflow.md); invariants in `premises.md` ("Prefabs are LINKED instances … (PF-C)" + "The prefab UX … (PF-D)").

- **Format + core (PF-C).** A `.mdprefab` reuses the `SceneData` schema verbatim through the same `CanonicalJson` + serializer registry. `PrefabWriter.BuildPrefab` validates exactly one root (`PrefabData.FindSingleRootIndex`), normalizes the root position to origin, drops any camera, and refuses cycles. ONE `PrefabExpander` reconstructs an instance (root + prefab-owned children, textures/`DrawComponent` restored, `PrefabInstanceComponent { PrefabId }` stamped, overrides applied) — shared by the scene reader (a `SceneSerializer.Deserialize` expander callback), the `PrefabFactory` (`EntitySpawnRequest("prefab:<id>")` prefix channel), and `PrefabPropagation.ReExpand` (live refresh on prefab-save; the Restart rule clears history when instances rebuild). Missing prefab ⇒ fail-loud; cycles capped at load. `PrefabFileSource` resolves an id to `PrefabData` source-first (`<ProjectRoot>/Prefabs/<id>.mdprefab`) then bundled (`TitleContainer`). `save → load → save` on a scene with instances is a byte fixed point.
- **The editable Inspector (PF-A).** The right-strip Inspector edits component members (`MemberEditCommand` — struct write-back), adds (`AddComponentCommand` — registry-driven candidates, `SpriteInfo⇔Draw` pairing) and removes (`RemoveComponentCommand`) components, all through the shared `EditorHistory`. This IS the prefab-assembly surface.
- **Viewport tabs (PF-B).** `ViewportContextStack` is the ONE tab-switch mechanism (snapshot → sweep → reader-restore); the Game tab is its discard consumer, prefab tabs its persistent ones (no camera — a prefab is a class).
- **Camera as entity (CM).** The authored camera is an ordinary `core.Camera` scene entity now — the editor rig is gone. `CameraEntityOverlay` owns only the frustum-glyph overlay; the camera entity border-picks on its frustum, `G`/`R` move+rotate its Transform, `S` edits `CameraComponent.Zoom` via the standard `MemberEditCommand`, and deleting the last camera is refused. `view:camera` / the header button snap the view onto it via `SnapViewToCameraEntity`. See [`docs/level-editor/camera-as-entity.md`](../../../docs/level-editor/camera-as-entity.md).
- **The UX (PF-D).** A Prefabs shelf tab; **Create Prefab from Selection** (capture → replace with a linked instance, one undoable composite) and **Create Empty Prefab**; prefab-context tabs; **Save Prefab** (`EditorOverlay.SavePrefabCurrent`) + propagation; **Unpack** (`UnpackPrefabCommand`); and the ONE `PrefabGuards.IsPrefabOwned` guardrail (the instance root stays editable, its children are refused). End-to-end acceptance: `MonoDreams.Tests/LevelEditor/PrefabMilestoneTests.cs`.

## Pipeline wiring (intended)

An editor-capable screen composes editor systems over the game pipeline in the *same* world through the `EditorPipelineRegistrar` (Wave 6): the reference composition is `LoadLevelExampleGameScreen` (in `MonoDreams.Examples.Core`) behind its `editorEnabled` flag, which the `--editor` run flag switches on for every registered screen. The game systems are wrapped per the interaction matrix in `docs/CORE_TENETS.md`:

- **`RunNormally`** (live in both modes): input mapping, `CursorInputSystem`, `CursorPositionSystem`; the whole render module (`CullingSystem`, `SpritePrepSystem`, `YSortSystem`, `MeshPrepSystem`, `TextPrepSystem`, `MasterRenderSystem`); and `HierarchySystem` (editor edits to a transform must still propagate to world space).
- **`Freeze`** (Play only): movement / velocity / physics / collision, NPC / dialogue, and `CameraFollowSystem` (in Edit the editor drives `Camera.Position`/`Zoom` directly — via `CameraNavSystem`).
- **Editor systems** (selection, gizmo, undo-apply, scene save/load, toolbar, camera-nav): registered always, but Edit-guarded so they are inert in `Play`. `CameraNavSystem` is ordered **before `CursorPositionSystem`** so a pan/zoom this frame is the camera state the cursor's world position derives from (no one-frame lag).

**Reaching the editor.** ONE door: launch the host with `--editor` (or `MONODREAMS_EDITOR=1`). Every screen then composes the overlay, the shell is always visible, and the transport boots Paused (see `EditorRunFlag` above). There is no menu entry and no dedicated editor screen — the old per-level "Edit" buttons and `LevelEditorScreen` were removed with the transport model; the menu's Play buttons behave exactly as in a plain run (they navigate while the transport is Playing; while Paused, `ui.interaction` is frozen so clicks belong to the editor).

Editor-overlay entities (gizmo, selection highlight, toolbar) are **standalone** — never parented via `ChildOfComponent` — so `HierarchySystem.DisposeOrphans` (live in Edit) cannot cascade-dispose them.

## Adding the editor to a screen/host

The editor never cares which host or screen it lands in — a menu, a demo, a level, a brand-new game. Making a new screen (or a whole new host, like `MonoDreams.Demos`) editor-capable is always the same four steps. Reference implementations: the Examples screens (`LevelSelectionScreen` / `LoadLevelExampleGameScreen` / `InfiniteRunnerScreen`), and the Demos screens + the `MonoDreams.Demos/DemoEditor.cs` helper that factors the shared construction for that host.

1. **Parse the run flag in the host.** In the host's `Game1` constructor: `_editor = EditorRunFlag.IsEnabled(args, Environment.GetEnvironmentVariable)`, then pass it into every screen factory as an `editorEnabled: _editor` ctor parameter. A host whose headless mode renders (the Demos host) honours the flag under `--headless` too — the shell lands in the captured frames, which is the observe-and-verify path.
2. **Build the screen's pipelines through `EditorPipelineRegistrar`** — both update AND draw — declaring each entry's edit policy at the registration site: game logic / simulation / UI-interaction `Freeze` (in Edit a click belongs to the editor, and live logic runs the scene out from under the gizmo — a live screen-transition button would even tear the screen down mid-editing); layout, render, cull/prep/sort, input, cursor, and `HierarchySystem` `RunNormally`. With the flag off every gate is a pass-through in Play and the screen is behaviourally identical — always build through the registrar so the flagged and unflagged compositions cannot drift.
3. **Compose the `EditorOverlay` under the flag** over the screen's **own** world/camera/layers, and weave its hooks at the documented points (the `EditorOverlay` class doc is authoritative; entry names use the `editor.*` convention so the systems panel groups them):
   - update: `editor.keys` (hosts without an action-mapping layer use the engine's `DefaultEditorKeys`; hosts with one, like Examples, wire their own action states into `EditorInputBindings`) → `editor.sceneReader` after input; `editor.commands` → `editor.gizmo` → `editor.proxySync` after the frozen logic block and **before** `hierarchy`; `editor.toolbar` → `editor.systemsPanel` (the left tabbed panel) → `editor.inspector` (the dedicated right Inspector) → `editor.cameraNav` **before** `cursorPosition`; `editor.palette` (only when the screen supplied an asset catalog + band map) right **after** `cursorPosition` — the ghost follows this frame's cursor world position; `editor.shell` after the cursor group; `editor.opDriver` last (when a headless op plan exists — also set the cursor input system's `SkipHardwareRead`).
   - draw: `editor.selection` after the prep/Y-sort group and before the render passes, then `editor.overlayPrep` (the overlay-visual emission — gizmo/selection/proxy meshes baked in screen pixels from the frame's final camera + selection) right after it; `editor.renderChrome` after the game passes and before `finalDraw`; append `overlay.ChromeLayer` **after** the game layers in the final-draw list.
   - Where the screen lacks a prerequisite the overlay supplies it or degrades gracefully: no cursor pipeline ⇒ `provideCursorPipeline: true`; no sprite prep ⇒ add cull → sprite-prep → Y-sort under the flag so loaded scenes preview; no Y-sorted `DrawLayerMap` layer (or a minimal map created just for the seam, like Demos' `DemoEditor.CreateLayers`) ⇒ Y-sort passes depths through and selection picks the final source-derived depth.
   - After both pipelines are built: `overlay.BindPipelines(update, draw)` + `EditorOverlay.LogComposition(screenName, update, draw)` — that log line is the observable contract the universal-overlay integration tests assert per screen.
4. **Boot the transport in the host.** After the `ScreenController` exists: `if (_editor) _screenController.State.RunMode = EditorRunFlag.InitialRunMode(true);` (Paused) and log the standard "Editor run flag active" message. `GameState` still constructs as `Play` — the boot mutation is an explicit host-level opt-in. Also resolve the versioned project once here — `var projectContext = _editor ? EditorProjectContext.Resolve() : null;` — and pass it into each screen factory (`projectContext: projectContext`) so the overlay can gate Save on it (unresolved ⇒ Save disabled with the "no project root" reason). A host with no project (e.g. the demos) simply passes null. **Rider:** set `MONODREAMS_PROJECT_ROOT` beside `--editor`.
5. **Record the reload in the screen's `Load`.** Once the screen knows what it loaded, set `overlay.Transport.Reload` to "re-publish my original load request" (the game screen re-publishes its `LoadLevelRequest`; a menu re-runs its UI builder) so the toolbar's Restart works; optionally set `overlay.Transport.KeepAlive` for screen infrastructure a system created at construction and holds by reference (e.g. the dialogue UI root via `DialogueStateComponent`). Without a `Reload`, Restart is a loud no-op.

## Cross-module dependencies

- `foundation` — `GameState.RunMode` + `GatedSystem` (the run-state model), `TransformComponent`, `ChildOfComponent`, `HierarchySystem`.
- `rendering` — the editor previews through the real `DrawComponent` pipeline + `Camera`; gizmo meshes use the mesh primitives.
- `ui` — the chrome reuses `SimpleButtonComponent` / `ButtonMeshPrepSystem` for panel + button meshes (on the native-resolution Editor target since Wave 7).
- `cursor` — selection and gizmo dragging read `CursorInputComponent.WorldPosition`.
- `collision` / `physics` — the serializer registry ships serializers for the collider/body components. Under colliders-as-entities (CE) a collider is its own entity: the editor selects / moves / scales it through the ordinary selection + gizmo path, and only a convex collider entity's per-vertex grips write back through `ColliderEditCommand.ForConvex` (refreshing the convex world data per the collision premises).
- `level-loading` — scene save/load reuses the spawn-request plumbing and the `IPlatformServices` storage seam; since PS5 the game boot is native-only (`LoadLevelRequest` → native reader, fail-loud otherwise) and the LDtk parser is import-only machinery (the `LoadSceneRequest`/`LoadLevelRequest` split is now a live-native-path vs import-op distinction, not a parallel-loaders one).

## Importing legacy levels (LDtk → native `.mdscene`)

`LevelImporter` (Composition) is the one-way import core: given a world a legacy parser populated, it
tags the scene-content roots (`SceneObjectComponent`, excluding editor-infra and bake products) and
serializes through the canonical `SceneWriter` to a native `.mdscene` the game then owns — reconstructed
on load by components, never by re-running the parser. The reference game drives it with a headless
export op (`Game1`: `--export-scene <id>` / `MONODREAMS_EXPORT_SCENE`, boots in Edit so frozen physics
can't perturb positions, excludes system-built UI like the dialogue sub-graph, writes into the project
source tree via `EditorProjectContext`). The Examples `Blender_Level` is already a committed native
`Content/Levels/Blender_Level.mdscene` (its origin was a Blender export; the game now owns it as a native scene, migrated once — there is no live Blender parser); the LDtk `Level_0` awaits a native tile-layer batching primitive
(a follow-up) before its ~21k per-tile entities can migrate. An editor toolbar "Import" action is a
natural next binding of the same core.

## Extension points

- **Game-component serialization (Wave 2, live; game serializers wired PS5).** Register `(write, read)` serializers for game-specific components (e.g. `PlayerState`) on the registry — `registry.Register(key, typeof(MyComponent), write, read)` — so they round-trip; the engine ships serializers for its own serializable components via `registry.RegisterEngineComponents()`. The reference game bundles its own via `GameComponentSerializers.RegisterGameComponents()` (PlayerState / OrbitalMotion / StopMotionEffect / DialogueZoneComponent), registered on BOTH the editor overlay's registry AND the shipped game's native-reader registry so a migrated native scene reconstructs game components with no editor composed. Only registered types serialize (opt-in); an unregistered component is skipped with a loud warning at write time.
- **Per-system edit-time policy.** Opt a system into freezing by wrapping it in `GatedSystem(child, EditTimeBehavior.Freeze)`; leave render/input/cursor/hierarchy ungated or `RunNormally`.
