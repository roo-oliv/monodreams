# level-editor — overview

The in-game level editor: an **Edit run mode** layered over the real game pipeline. The editor is not a separate application or renderer — it is a mode of the game (see `docs/CORE_TENETS.md`, "The editor is part of the game"). In `Edit`, the same world, the same `Camera`, and the same `CullingSystem → SpritePrepSystem → YSortSystem → MasterRenderSystem` draw stack the player sees stay live; game logic, physics, and camera-follow freeze; and editor tooling (selection, gizmos, undo, scene save/load, toolbar) runs on top.

> **Status: Wave A complete (Waves 1–5) + post-Wave-A editor usability.** Wave 1 shipped the run-state model (in `foundation`) and the docs that codify it. Wave 2 added the **native scene format** + the **component-serializer registry** (under `Serialization/`) and an additive `AssetKey` on `SpriteInfoComponent`. Wave 3 added the **scene round-trip** (`SceneObjectComponent`, `SceneWriter`, `LoadSceneRequest` + `SceneReaderSystem`, `IPlatformServices.ExportScene`). Wave 4a added the **interactive-editor substrate**: the reference `LevelEditorScreen` (in `MonoDreams.Examples.Core`) that composes the gated game pipeline + editor systems in one world with an in-place `RunMode` toggle; `SelectedComponent` + `EditorIdComponent` + `SelectionSystem` (click-to-pick the frontmost sprite); the `EditorHistory` bounded undo/redo with drag-coalescing + the `IEditorCommand` abstraction and the create/delete/transform commands; and the `EditorModeToggleSystem` / `EditorCommandSystem`. Wave 4b added the **transform gizmo** (`GizmoSystem` + `GizmoStateComponent` / `GizmoOverlayComponent` + the pure `Transform/GizmoTransform` math — move/rotate/scale handles, a selection outline, grid-snap, a drag coalesced into one undo step) and the **engine-native toolbar** (`ToolbarSystem` + `Component/ToolbarButtonComponent` + `UI/EditorToolbarBuilder` — tool-select/Save/Load/Undo/Redo/snap on the HUD target). Wave 5 added the **headless editor-op channel** (`Channel/EditorOpPlan` + `Channel/EditorOpReplaySystem`) plus the `CursorInputSystem.SkipHardwareRead` seam, so the real editor systems run headless with no real mouse. **Post-Wave-A usability** added **editor camera navigation** (`CameraNavSystem` + the pure `Navigation/CameraNav` math — middle-mouse pan, scroll-wheel zoom, and a frame-scene key that centres + zoom-fits the camera on all content so off-origin levels are reachable) and a **menu entry into the editor** (a per-level "Edit" button in `LevelSelectionScreen` that reuses the existing `ScreenTransitionRequest` → `RequestedLevelComponent` path to boot `LevelEditorScreen` on that level). **Wave 6** extracted the whole editor block into the reusable **composition seam** (under `Composition/`): the `EditorPipelineRegistrar` (named, gate-wrapped, runtime-toggleable pipeline entries — the systems panel's binding surface), the `EditorOverlay` (registry/serializer/history + every editor system + the toolbar + the headless channel, built over the screen's own world), and the `EditorRunFlag` (`--editor` / `MONODREAMS_EDITOR=1` — the plain game screen composes the overlay and the game boots in Edit). **Wave 7** added the **Blender-style editor shell**: in Edit the game composite renders into a smaller centered viewport (`ViewportManager.SetViewportInset` — compositing and mouse mapping follow the same rect) with the chrome placed *around* it at **native window resolution** (`RenderTargetID.Editor` + `EditorChromeRenderSystem` + `RenderLayer.Native`): opaque dark panels (top toolbar bar, right panel strip reserved for the Wave-8 systems panel, bottom strip — `UI/EditorChromeLayout` + `UI/EditorChromeBuilder`) and the toolbar rebuilt in real pixels (hit-testing raw `ScreenPosition`), all synced with the run mode by `EditorShellSystem` (which also swaps to the OS cursor over chrome in Edit). The old HUD-virtual toolbar builder is retired. **Wave 8a** made the overlay **universal** (under the run flag every Examples screen composes it — the menu and the infinite runner included; the overlay can supply its own cursor pipeline to a cursor-less screen via `provideCursorPipeline`), made selection + the gizmo **target-aware** (UI/HUD-target sprites hit-test/drag in virtual space via `VirtualPosition`; across targets the composite order wins — UI/HUD above Main; the gizmo overlays draw on the selected entity's own target), and shipped the **systems panel** (`System/SystemsPanelSystem` + the pure `UI/SystemsPanelLayout`) in the shell's right strip: every registrar entry of both pipelines, in order, as name + policy tag + live enabled checkbox, toggled through `EditorPipelineRegistrar.SetEnabled`. **Wave 8b** added the **collider gizmo proxies**: colliders are component-local spatial data (not entities), so `System/ProxySyncSystem` materializes standalone proxy entities (`GizmoProxyComponent` bindings under `Component/`, geometry under `Proxy/ProxyGeometry`) over the selected entity's collider shapes; they join the same selection pick (border-only hit-test) and the same gizmo drag (move tool), writing back into the bound component through `Undo/ColliderEditCommand` (one undo step per drag; convex writes refresh `WorldVertices`/`BroadPhaseAABB`). **Post-Wave-8b host wiring** extended the universal overlay **across hosts**: the Demos host (the launcher menu + all four module demo screens) composes it under the same run flag, pairing the overlay with the engine's new `DefaultEditorKeys` default keyboard surface (for hosts without their own action mapping) — the step-by-step recipe any new host/screen follows is [Adding the editor to a screen/host](#adding-the-editor-to-a-screenhost) below. Anything not yet built is marked **(planned, Wave N)**.

## Purpose

A game built on MonoDreams should be editable *inside the running game*, previewing exactly what the player sees rather than approximating it in a bespoke editor renderer. The editor achieves this by gating the game pipeline on an engine-wide run state instead of forking it: each game system is wrapped (opt-in) in a `GatedSystem` carrying an `EditTimeBehavior` policy, and flipping `GameState.RunMode` from `Play` to `Edit` enters/exits editing with no screen swap, preserving all in-world state.

## What ships

### Run-state foundation (ships in `foundation`, Wave 1)

The editor's cornerstone is not in this module — it is in `foundation`, because every screen (editor or not) must understand it:

- `RunMode` enum (`Play` / `Edit`) + `GameState.RunMode` property (default `Play`).
- `EditTimeBehavior` enum (`RunNormally` / `Freeze` / `RunPartial` / `RuntimeEditable`).
- `GatedSystem` — an `ISystem<GameState>` decorator that wraps a child system + a policy and runs the child only when the run mode admits it.

See `MonoDreams/foundation/docs/premises.md` ("Edit-time behavior is a per-system policy honored by `GatedSystem`" and "Default `RunMode = Play` preserves all existing pipelines").

### Serialization (Wave 2, live — under `Serialization/`)

The scene-persistence substrate. It is infrastructure (services), not components — ECS purity keeps components pure data and puts the read/write behaviour in the registry/serializers.

- `SceneData` / `SceneEntityData` / `SceneCameraData` / `SceneLayerData` — the in-memory model of a native scene (1:1 with `scene-format.md`): `version`, `camera`, `layers[]`, a reserved `sources[]`, and `entities[]` (each a `components{}` map + an optional `parent` index).
- `ComponentSerializer` — a `(write, read)` pair for one component `Type`, keyed by a stable string.
- `ComponentSerializerRegistry` — the opt-in registry (`Type` → serializer). Discovers every component on an entity via DefaultEcs `ReadAllComponents`, writes the registered ones, and emits a `Logger.Warning` for any unregistered one (skip, never silent drop). Loading an unregistered component key throws (fail loud).
- `EngineComponentSerializers.RegisterEngineComponents` — registers the engine's serializers (`Transform`, `SpriteInfo`, `EntityInfo`, the colliders, `RigidBody`, `Velocity`, the `ChildOf` parent link). Centralized here because this module already depends on the modules those components live in.
- `SceneSerializer` — the in-memory round-trip seam: serializes a set of entities to `SceneData` (preserving the `ChildOf` parent graph as indices) and reconstructs them in two passes (create + deserialize, then wire parents). Wave 3 layers JSON file I/O + `LoadSceneRequest` + `Texture2D` rehydration on top.

### Components

- `SceneObjectComponent` (Wave 3, live, under `Component/`) — a pure tag marking a **save-root** entity; the `SceneWriter` includes each tagged root plus its `ChildOfComponent` descendant closure.
- `SelectedComponent` (Wave 4a, live, under `Component/`) — a pure tag marking the currently-selected entity for the gizmo and toolbar (single-select; transient, not serialized).
- `EditorIdComponent` (Wave 4a, live, under `Component/`) — a stable monotonic id the selection system assigns to each candidate the first time it sees it; the selection-owned tiebreak for an exact-depth pick (the renderer's insertion index is private).
- `GizmoStateComponent` (Wave 4b, live, under `Component/`) — the gizmo's configuration (active `GizmoTool`, `SnapEnabled`, `GridStep`, `RotationStepRadians`); a single editor-owned entity the toolbar mutates and `GizmoSystem` reads. Pure data — the per-drag accumulation is `GizmoSystem`'s private frame state.
- `GizmoOverlayComponent` (Wave 4b, live, under `Component/`) — tags the gizmo's own overlay mesh entities (the selection outline + the move/rotate/scale handles) so the system can manage them. They are standalone (never `ChildOfComponent`-parented) and set `VisibleComponent` themselves.
- `ToolbarButtonComponent` (Wave 4b, live, under `Component/`) — tags a toolbar button with its `EditorToolbarAction` + its `Bounds` for `ToolbarSystem`'s hit-test (since Wave 7: physical screen pixels, tested against the cursor's raw `ScreenPosition`).
- `GizmoProxyComponent` + `ProxyBindingKind` (Wave 8b, live, under `Component/`) — the pure-data binding of an edit-time gizmo proxy: the bound target entity, which spatial field it edits (`BoxColliderBounds` / `ConvexColliderShape`), and a reserved `Index` for future sub-element bindings (per-vertex handles; the road tool's spline control points, Waves D/F). The proxy entity itself is a standalone overlay (own `TransformComponent` at the shape's world centre, cyan outline mesh, self-`VisibleComponent`), transient and never serialized.

### Systems

- `SceneReaderSystem` (Wave 3, live, under `System/`) — subscribes to `LoadSceneRequest`, reads the scene JSON (content stream via `TitleContainer`, or `IPlatformServices` for host-filesystem user data), deserializes via the Wave-2 `SceneSerializer` (two-pass create + deserialize + parent-wire), rehydrates each sprite's `Texture2D` from its `AssetKey`, and fails loud on an unregistered component key. The texture loader is injectable (`Func<string, Texture2D>`) so it is unit-testable without a `GraphicsDevice`.
- `SelectionSystem` (Wave 4a, live, under `System/`; target-aware since Wave 8a) — on a left-button press in Edit, hit-tests the cursor against each rendered sprite's quad (`SpriteHitTest`, honoring rotation/scale/origin/offset) and selects the frontmost. Main-target sprites test the cursor's `WorldPosition`; UI/HUD/Scroll-target sprites test `VirtualPosition` (their transforms are virtual coordinates); the Editor target (chrome) is never a candidate. Across targets the composite order ranks (Main < UI < HUD < Scroll); within a target it is MAX final post-YSort `DrawComponent.LayerDepth`, tiebroken by `EditorIdComponent`. Ordered at the end of the draw pipeline so it reads the final depth this frame; Edit-guarded; click-empty clears.
- `EditorModeToggleSystem` (Wave 4a, live, under `System/`) — flips `GameState.RunMode` Play↔Edit in place (no screen swap) when a `Func<GameState,bool>` predicate fires.
- `EditorCommandSystem` (Wave 4a, live, under `System/`) — Edit-guarded; translates delete/undo/redo intent into `EditorHistory` operations (delete builds a sub-graph-snapshotting `DeleteEntityCommand`).
- `GizmoSystem` (Wave 4b, live, under `System/`; target-aware since Wave 8a) — reads `SelectedComponent`, draws the move/rotate/scale handle + a selection outline as standalone overlay mesh entities (self-`VisibleComponent`), hit-tests the active handle, and on a drag opens an `EditorHistory` transaction, pushes a `TransformEditCommand` each frame (computed by the pure, space-agnostic `GizmoTransform`, applying grid-snap), and commits on release → one undo step. A Main-target selection works in world space (cursor `WorldPosition`, overlays on Main, handles sized by `1/Camera.Zoom`); a UI/HUD-target selection works in virtual space (cursor `VirtualPosition`, overlays on the entity's own target, no zoom compensation). Inert + overlays torn down in Play. Runs before `HierarchySystem` so the edit propagates the same frame.
- `ToolbarSystem` (Wave 4b, live, under `System/`; retargeted Wave 7) — Edit-guarded; hit-tests the cursor's raw `ScreenPosition` (physical pixels — the chrome is native-resolution) against each `ToolbarButtonComponent.Bounds`, tints the hovered button's fill, and hands a click's `EditorToolbarAction` to a game-supplied dispatch. No Play-mode blanking anymore: the chrome render pass simply doesn't run outside Edit.
- `CameraNavSystem` (post-Wave-A, live, under `System/`) — Edit-guarded camera navigation: middle-mouse **pan** (the camera moves opposite the cursor's virtual-pixel delta, scaled by `1/Zoom`, so the grabbed world point stays put), scroll-wheel **zoom** (a geometric step on `Camera.Zoom`, clamped 0.25–4.0), and **frame-scene** (a key edge centres + zoom-fits the camera on the AABB of all `SpriteInfoComponent` content; no content = no-op). Drives `Camera.Position`/`Zoom` directly (the editor owns the camera in Edit; `CameraFollowSystem` is `Freeze`-gated). Registered **before `CursorPositionSystem`** so the camera mutation is the camera the cursor's world-pos derives from that same frame. Inert in Play.
- `Transform/GizmoTransform` (Wave 4b, live) — the pure, GraphicsDevice-free transform math behind the gizmo (move/rotate/scale + grid-snap, honoring Origin); separated from `GizmoSystem` so it is directly unit-testable. Its `SpriteWorldQuad` corner helper is reused by `CameraNavSystem`'s frame-scene to compute the content AABB.
- `Navigation/CameraNav` (post-Wave-A, live) — the pure, world-free math behind `CameraNavSystem` (pan sign + zoom-clamp + content-AABB centre/fit); separated from the system so it is directly unit-testable without a real `Camera` or cursor (mirrors the `GizmoTransform` split).
- `UI/EditorChromeLayout` (Wave 7, live) — the pure, world-free layout math of the shell (panel rectangles, toolbar button row, the `ViewportInset` margins) in physical screen pixels; the same numbers feed both the chrome entities and `ViewportManager.SetViewportInset`, so the panels always exactly cover the reserved margins.
- `UI/EditorChromeBuilder` (Wave 7, live; replaces the Wave-4b `EditorToolbarBuilder`) — builds the native-resolution chrome on `RenderTargetID.Editor`: opaque panel backgrounds (fill-only `SimpleButtonComponent` meshes) + the toolbar's labelled buttons (each tagged `ToolbarButtonComponent`), with `Relayout(w,h)` recomputing everything on window resize. Labels are the screen's 48px BitmapFont at 1/3 scale (≈16px), rendered directly at native res. Chrome entities carry **no `VisibleComponent`** (it would pull the meshes into `MeshPrepSystem`, which overwrites the identity `WorldMatrix` their absolute-pixel vertices require). No ImGui; web-capable.
- `System/EditorShellSystem` (Wave 7, live) — syncs the shell with the run mode every frame: applies/clears the viewport inset, relayouts the chrome when the window size changes, and swaps the pointer (OS cursor over chrome in Edit; game cursor sprite in Play). Its `Dispose` clears the inset + re-hides the OS cursor so a screen swap never leaks the shell.
- `System/EditorChromeRenderSystem` (Wave 7, live) — the chrome's render pass: a screen-space `MasterRenderSystem` over `RenderTargetID.Editor` into a native window-resolution target recreated on resize; outside Edit it renders nothing and exposes a null `CurrentTarget`, making the `RenderLayer.Native` final-draw layer skip entirely.
- `System/SystemsPanelSystem` + `UI/SystemsPanelLayout` (Wave 8a, live) — the systems panel in the shell's right strip: lists every `EditorPipelineRegistrar` entry of both bound pipelines (update, then draw, in execution order) as name + policy tag (`[freeze]` etc.) + a checkbox reflecting the live enabled state; a row click toggles the entry via `SetEnabled` (a both-modes master switch; the panel refuses to disable its own entry), the wheel scrolls whole lines over the strip, and rows are ordinary native-pixel chrome entities (no `VisibleComponent`, `ScreenPosition` hit-test) laid out by the pure layout class. Binds lazily via `EditorOverlay.BindPipelines`.
- `System/ProxySyncSystem` + `Proxy/ProxyGeometry` (Wave 8b, live; registrar entry `editor.proxySync`, woven right after `editor.gizmo`) — materializes the collider gizmo proxies: when the selected entity in Edit carries collider components, one standalone proxy entity per collider is spawned (cyan `1/Zoom`-thick outline, `LayerDepth 0.998`, on Main) and re-derived from the bound component every frame (tracking both owner moves and the same frame's gizmo write-back); despawned on deselect / mode exit / target death; selecting a proxy keeps its family alive (the anchor follows the proxy's target). It also refreshes the selected entity's convex `WorldVertices` per frame (physics is frozen in Edit) so the `ColliderDebugSystem` outline stays coherent — the two coexist: the debug system is the global selection-unaware diagnostic, the proxy is the selected-entity edit affordance, independent of the debug flag. `ProxyGeometry` is the pure single source of truth for the shape derivations (box corners, convex world vertices mirroring `UpdateWorldVertices`, centroid, border distance, world→model delta inversion) shared by the sync, the selection border pick, and the gizmo write-back.

### Undo (Wave 4a, live — under `Undo/`)

- `IEditorCommand` — a reversible editor mutation as DATA + an `Apply`/`Revert` pair (ECS purity: not a behavior-laden OO object).
- `EditorHistory` — bounded undo/redo (configurable cap, oldest-evicted FIFO; empty-stack no-op) with the drag-coalescing transaction API (`BeginTransaction`/`CommitTransaction`/`CancelTransaction` → one entry per drag).
- `CompositeCommand` — bundles a coalesced transaction's commands into one undo step.
- `CreateEntityCommand` / `DeleteEntityCommand` — create tags the new root `SceneObjectComponent` + snapshots its sub-graph; delete snapshots the disposed sub-graph (reusing `SceneSerializer`) so undo restores it whole. `EntitySubgraph.Collect` is the shared `ChildOf` descendant-closure walk.
- `TransformEditCommand` — a before/after transform edit; `GizmoSystem` (Wave 4b) constructs it via `FromCurrent` each drag frame and the coalescing transaction collapses the drag into one entry.
- `ColliderEditCommand` (Wave 8b) — a before/after edit of a collider's component-local spatial data (`BoxColliderComponent.Bounds` / `ConvexColliderComponent.ModelVertices`), always targeting the **bound game entity** (never the transient proxy); convex writes refresh `WorldVertices` + `BroadPhaseAABB` (physics is frozen in Edit). Pushed per proxy-drag frame inside the coalescing transaction, like `TransformEditCommand`.

### Serialization writer (Wave 3, live — under `Serialization/`)

- `SceneWriter` — computes the membership closure (`SceneWriter.CollectMembership`: every `SceneObjectComponent` root + each one's `ChildOfComponent` descendants), serializes it through the Wave-2 `SceneSerializer` into a `SceneData` (attaching `Camera` state + the `DrawLayerMap` banding), JSON-serializes it, and exports through `IPlatformServices.ExportScene`. Save-time only — never per frame.

### Headless editor-op channel (Wave 5, live — under `Channel/`)

- `EditorOpPlan` / `EditorOp` — a scripted plan of editor operations (`MoveCursor` / `LeftDown` / `LeftUp` / `ToggleMode` / `ToolbarAction`, each on a frame index) the test analogue of `InputReplayPlan` (which scripts keyboard edges). `EditorOpPlan.TryLoad` reads `editor_op_plan.json` from the debug dir (mirrors `InputReplayPlan.TryLoad`).
- `EditorOpReplaySystem` — consumes the plan and, with **no real mouse**, injects `CursorInputComponent` state (world/virtual position + the left-button press/release edges) onto the cursor, toggles `GameState.RunMode`, and fires toolbar actions through a dispatch callback. It **holds the session open** (requests exit only after the op queue drains + a tail) so the input-replay auto-exit-on-drain can't kill the editor-op run early. Registered only when a plan is present (zero cost in a normal Play run). Pairs with `CursorInputSystem.SkipHardwareRead` (the per-frame hardware read is skipped so the injected cursor survives).

### Messages

- `LoadSceneRequest` (Wave 3, live, under `Message/`) — loads a native MonoDreams scene file; distinct from `LoadLevelRequest` so it never triggers the LDtk `Content.Load` / `Remove<CurrentLevelComponent>` path. Carries the scene `Path` and a `FromContent` flag (content asset vs. host-filesystem user data).

### Composition (Wave 6, live — under `Composition/`)

The reusable seam that turns any screen into an editor-capable screen:

- `EditorPipelineRegistrar` — the pipeline **composition seam**: a screen registers each pipeline entry (`Add(name, system, policy, enabledInEditByDefault?)`), every entry is wrapped in a `GatedSystem` per its declared policy, and `Build()` produces the final `SequentialSystem<GameState>`. The registrar **retains** the ordered entry registry at runtime (`Entries`, `SetEnabled(name, bool)` — a master toggle that stops a system in BOTH modes, `GetEntry`) — the seam the upcoming systems panel binds to. The edit-mode default is declared at the registration site, never by an interface on the system type (the same engine system may need different policies in different games); an `enabledInEditByDefault` that contradicts the policy throws until the runtime per-mode policy override lands (a documented systems-panel follow-up).
- `EditorOverlay` — everything a screen needs to become editor-capable, built over the screen's own world/camera/layers: the shared `ComponentSerializerRegistry` + `SceneSerializer` + bounded `EditorHistory` + the single gizmo-state entity; every editor system (`ModeToggle`, `SceneReader`, `EditorCommands`, `Gizmo`, `Toolbar` incl. `ButtonMeshPrepSystem`, `CameraNav`, `Shell`, the draw-side `Selection` + `ChromeRender`, and the plan-gated `EditorOpDriver`); the native-resolution chrome entities (`Chrome`) + the `ChromeLayer` final-draw layer; and the toolbar dispatch wired to those same shared instances. The overlay exposes the systems as individual hooks (they interleave with the game pipeline at documented points — see the class doc) and receives the screen's registrars via `BindPipelines` so editor tooling can enumerate/toggle the live pipeline.
- `EditorInputBindings` — the game-specific input surface (five just-pressed predicates over `GameState`); keeps the overlay and every editor system free of any game input enum.
- `DefaultEditorKeys` (post-Wave-8b, live) — the editor's default keyboard surface for hosts **without** their own keyboard-action mapping layer (the Demos host; any new host): one `AKeyboardInputHandlingSystem` over the standard editor keys — F1 (Play↔Edit), Delete, Z (undo), Y (redo), Home (frame scene) — exposing ready-made `Bindings` (an `EditorInputBindings`) backed by its own per-action edge states. Weave it as the `editor.keys` registrar entry before `editor.modeToggle`. A host that already maps actions (the Examples `InputMappingSystem`) keeps wiring its own action states instead.
- `EditorRunFlag` — the "editor everywhere" run configuration: `--editor` launch arg or `MONODREAMS_EDITOR=1` env var (pure `IsEnabled(args, getEnv)` parse + `InitialRunMode`). When active the desktop head composes the overlay into the plain game screen and boots `ScreenController.State.RunMode = Edit` (no F1 needed; F1 still toggles). **Rider:** add `--editor` to Program arguments, or `MONODREAMS_EDITOR=1` to Environment variables, of the `MonoDreams.Examples.Desktop` run configuration.

## Pipeline wiring (intended)

An editor-capable screen composes editor systems over the game pipeline in the *same* world through the `EditorPipelineRegistrar` (Wave 6): the reference composition is `LoadLevelExampleGameScreen` (in `MonoDreams.Examples.Core`) behind its `editorEnabled` flag — `LevelEditorScreen` is that screen with the flag pinned on, and the `--editor` run flag registers even `ScreenName.Game` with it. The game systems are wrapped per the interaction matrix in `docs/CORE_TENETS.md`:

- **`RunNormally`** (live in both modes): input mapping, `CursorInputSystem`, `CursorPositionSystem`; the whole render module (`CullingSystem`, `SpritePrepSystem`, `YSortSystem`, `MeshPrepSystem`, `TextPrepSystem`, `MasterRenderSystem`); and `HierarchySystem` (editor edits to a transform must still propagate to world space).
- **`Freeze`** (Play only): movement / velocity / physics / collision, NPC / dialogue, and `CameraFollowSystem` (in Edit the editor drives `Camera.Position`/`Zoom` directly — via `CameraNavSystem`).
- **Editor systems** (selection, gizmo, undo-apply, scene save/load, toolbar, camera-nav): registered always, but Edit-guarded so they are inert in `Play`. `CameraNavSystem` is ordered **before `CursorPositionSystem`** so a pan/zoom this frame is the camera state the cursor's world position derives from (no one-frame lag).

**Reaching the editor.** Two doors, one composition. (1) The menu: a game opts a level into editing by registering `LevelEditorScreen` under `ScreenName.LevelEditor` and routing to it with a `RequestedLevelComponent` set. The reference menu (`LevelSelectionScreen`) gives each editable level a per-level **Edit** button whose `LevelSelector.TargetScreen = ScreenName.LevelEditor`; the shared `ButtonInteractionSystem` publishes `ScreenTransitionRequest(LevelEditor, levelId)`, and the existing handler stashes the `RequestedLevelComponent` + loads the editor — the same generalized transition path the Play buttons use, only the target-screen data differs. (2) The run flag: launch the desktop head with `--editor` (or `MONODREAMS_EDITOR=1`) and the plain game screen composes the overlay too, booting straight into Edit — no F1, no menu detour (see `EditorRunFlag` above).

Editor-overlay entities (gizmo, selection highlight, toolbar) are **standalone** — never parented via `ChildOfComponent` — so `HierarchySystem.DisposeOrphans` (live in Edit) cannot cascade-dispose them.

## Adding the editor to a screen/host

The editor never cares which host or screen it lands in — a menu, a demo, a level, a brand-new game. Making a new screen (or a whole new host, like `MonoDreams.Demos`) editor-capable is always the same four steps. Reference implementations: the Examples screens (`LevelSelectionScreen` / `LoadLevelExampleGameScreen` / `InfiniteRunnerScreen`), and the Demos screens + the `MonoDreams.Demos/DemoEditor.cs` helper that factors the shared construction for that host.

1. **Parse the run flag in the host.** In the host's `Game1` constructor: `_editor = EditorRunFlag.IsEnabled(args, Environment.GetEnvironmentVariable)`, then pass it into every screen factory as an `editorEnabled: _editor` ctor parameter. A host whose headless mode renders (the Demos host) honours the flag under `--headless` too — the shell lands in the captured frames, which is the observe-and-verify path.
2. **Build the screen's pipelines through `EditorPipelineRegistrar`** — both update AND draw — declaring each entry's edit policy at the registration site: game logic / simulation / UI-interaction `Freeze` (in Edit a click belongs to the editor, and live logic runs the scene out from under the gizmo — a live screen-transition button would even tear the screen down mid-editing); layout, render, cull/prep/sort, input, cursor, and `HierarchySystem` `RunNormally`. With the flag off every gate is a pass-through in Play and the screen is behaviourally identical — always build through the registrar so the flagged and unflagged compositions cannot drift.
3. **Compose the `EditorOverlay` under the flag** over the screen's **own** world/camera/layers, and weave its hooks at the documented points (the `EditorOverlay` class doc is authoritative; entry names use the `editor.*` convention so the systems panel groups them):
   - update: `editor.keys` (hosts without an action-mapping layer use the engine's `DefaultEditorKeys`; hosts with one, like Examples, wire their own action states into `EditorInputBindings`) → `editor.modeToggle` → `editor.sceneReader` after input; `editor.commands` → `editor.gizmo` → `editor.proxySync` after the frozen logic block and **before** `hierarchy`; `editor.toolbar` → `editor.systemsPanel` → `editor.cameraNav` **before** `cursorPosition`; `editor.shell` after the cursor group; `editor.opDriver` last (when a headless op plan exists — also set the cursor input system's `SkipHardwareRead`).
   - draw: `editor.selection` after the prep/Y-sort group and before the render passes; `editor.renderChrome` after the game passes and before `finalDraw`; append `overlay.ChromeLayer` **after** the game layers in the final-draw list.
   - Where the screen lacks a prerequisite the overlay supplies it or degrades gracefully: no cursor pipeline ⇒ `provideCursorPipeline: true`; no sprite prep ⇒ add cull → sprite-prep → Y-sort under the flag so loaded scenes preview; no Y-sorted `DrawLayerMap` layer (or a minimal map created just for the seam, like Demos' `DemoEditor.CreateLayers`) ⇒ Y-sort passes depths through and selection picks the final source-derived depth.
   - After both pipelines are built: `overlay.BindPipelines(update, draw)` + `EditorOverlay.LogComposition(screenName, update, draw)` — that log line is the observable contract the universal-overlay integration tests assert per screen.
4. **Boot the run mode in the host.** After the `ScreenController` exists: `if (_editor) _screenController.State.RunMode = EditorRunFlag.InitialRunMode(true);` and log the standard "Editor run flag active" message. `GameState` still constructs as `Play` — the boot mutation is an explicit host-level opt-in.

## Cross-module dependencies

- `foundation` — `GameState.RunMode` + `GatedSystem` (the run-state model), `TransformComponent`, `ChildOfComponent`, `HierarchySystem`.
- `rendering` — the editor previews through the real `DrawComponent` pipeline + `Camera`; gizmo meshes use the mesh primitives.
- `ui` — the chrome reuses `SimpleButtonComponent` / `ButtonMeshPrepSystem` for panel + button meshes (on the native-resolution Editor target since Wave 7).
- `cursor` — selection and gizmo dragging read `CursorInputComponent.WorldPosition`.
- `collision` / `physics` — the serializer registry ships serializers for the collider/body components, and the Wave-8b gizmo proxies read + write `BoxColliderComponent` / `ConvexColliderComponent` directly (refreshing the convex world data per the collision premises).
- `level-loading` — scene save/load reuses the spawn-request plumbing and the `IPlatformServices` storage seam; the native `LoadSceneRequest` is deliberately separate from the LDtk/Blender `LoadLevelRequest`.

## Extension points

- **Game-component serialization (Wave 2, live).** Register `(write, read)` serializers for game-specific components (e.g. `PlayerState`) on the registry — `registry.Register(key, typeof(MyComponent), write, read)` — so they round-trip; the engine ships serializers for its own serializable components via `registry.RegisterEngineComponents()`. Only registered types serialize (opt-in); an unregistered component on an entity is skipped with a loud warning at write time.
- **Per-system edit-time policy.** Opt a system into freezing by wrapping it in `GatedSystem(child, EditTimeBehavior.Freeze)`; leave render/input/cursor/hierarchy ungated or `RunNormally`.
