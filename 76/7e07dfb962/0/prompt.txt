> Claude Opus 4.7:
Sim, existe um padrão bem definido e é exatamente o que está virando estado da arte em frameworks AI-friendly: o **modelo shadcn** (também chamado de "Open Code" ou "code distribution"). Não é git submodule, é mais sofisticado.

A ideia central: você não distribui pacote opaco via npm/PyPI. Distribui código-fonte que é **copiado** para o projeto do usuário via CLI. O usuário literalmente possui aquele código, modifica, versiona junto com o app. Tipo "vendoring intencional como first-class citizen".

**Por que isso bate Spring-style para AI:**

1. **Código visível ao agente.** Ele lê tudo no repo do usuário. Contrasta com herdar de classes base do Spring, onde o agente depende de conhecimento prévio ou tem que ler fontes externas.
2. **Modificação direta.** Sem `extends`, `@Override`, ou extension functions só pra customizar. O agente edita o código in-place.
3. **Sem indireção mágica.** Reflection, proxies, autoconfiguration são hostis pra LLM porque o comportamento não está visível no código.
4. **Cada projeto vira único.** Não existe "versão do framework", existe "estado do código gerado".

**Evolução importante: shadcn registry**

shadcn começou só com componentes React, mas em 2024-2025 evoluiu pra um padrão genérico de distribuição. Qualquer um pode publicar uma `registry.json` (descreve arquivos, dependências, hooks de instalação) e a CLI resolve e copia. Funciona pra qualquer linguagem/framework. Arquitetura típica em três camadas:

- **Core lib pequena** distribuída como package normal (primitivas, tipos, utilitários)
- **Registry de blocks/recipes** com código copiável (handlers, integrações, padrões)
- **CLI** que resolve dependências e copia arquivos

Outros exemplos no mesmo padrão: Better Auth (TS), partes do Vercel AI SDK, Convex Components, Composio, e o ecossistema todo de "shadcn-style" registries (tremor, magicui, kibo-ui).

**No mundo Python**

Ainda é mais raro, mas existe:

- **copier** (sucessor moderno do cookiecutter) é o que mais se aproxima. Crítico: suporta **updates** via `copier update` com merge de conflitos. É o ponto fraco do shadcn original resolvido desde a fundação.
- **uv** tem `uv init --template` indo nessa direção.
- FastAPI não tem oficial, mas a comunidade trabalha com repos "fastapi-best-practices" como template implícito.

**O problema real do padrão (e onde IA muda o jogo)**

O furo clássico: depois que copiei o código, como recebo updates upstream? Abordagens:

1. Não recebe (shadcn original assumia isso, "é seu agora").
2. Re-run da CLI com diff seletivo (shadcn moderno).
3. Merge tooling de template (copier).

IA muda isso fundamentalmente: o agente pode aplicar updates **semanticamente**, não textualmente. Você publica "migration notes" no registry ("renomeei `handleX` pra `processX`, mudou assinatura, aqui está a intenção") e o agente aplica no fork do usuário entendendo o contexto, não fazendo patch. Esse padrão ainda não tem nome consagrado mas tá sendo experimentado via Claude Code skills, Cursor rules, Continue.dev.

**AI-native specifics pro teu framework**

Coisas que valeria desenhar desde o início:

- **AGENTS.md / llms.txt por bloco** no registry, com instruções de quando e como usar.
- **Schemas estruturados** (JSON Schema ou similar) descrevendo o que cada módulo expõe, pro agente raciocinar sem ler todo código primeiro.
- **MCP server oficial do framework** que expõe registry + docs + exemplos. Quando o usuário tá num agente, ele consulta na hora de gerar.
- **Convenções fortes mas explicitamente documentadas em texto.** Rails-style, mas o "magic" tem que estar verbalizado pro agente.
- **Decisões de design auditáveis no código gerado.** Comentários estratégicos do tipo "este handler usa X porque Y" ajudam o agente em refatorações futuras sem precisar reler docs.

**Recomendação prática**

Como referência arquitetural, estuda o `shadcn` CLI e o schema do `registry.json` deles (modelo é portável pra Python). Pra Python especificamente, considera usar `copier` como base e construir um CLI por cima, ou inspirar-se nele. O update story do copier resolve um problema que o shadcn ainda apanha.

Se quiser, posso entrar em algum aspecto específico. O que muda bastante a recomendação é o domínio: framework web genérico, agentic AI runtime, data pipelines, etc. Cada um tem trade-offs diferentes na granularidade do que é "block".
