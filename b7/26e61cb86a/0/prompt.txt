`implement` executa um plano aprovado até virar um Pull Request aberto, e então encadeia o `/review-fix-loop`. A implementação roda dentro de um **Workflow** (`~/.claude/workflows/implement.js`) — esta invocação de skill é o opt-in explícito do usuário para a orquestração multi-agente, incluindo a autorização expressa para os agentes do workflow **commitarem e darem push na branch de trabalho** (somente nela; nunca em `main`, nunca force).

Arquitetura de contexto: **waves + ledger**. O script divide o plano em ondas; cada onda é um agente *fresco* que lê o plano + o ledger de progresso, implementa só a sua fatia, verifica, commita, dá push e atualiza o ledger. Nenhum agente acumula contexto além da própria onda — esse é o substituto do `/compact` (não invocável dentro de agentes de workflow) — e um crash é retomável a partir do ledger + branch.

---

## Passo 1 — Parse dos argumentos

- Detecte e remova o token `no-review` (alias: `noreview`, `sem-review`) → seta `NO_REVIEW`.
- O restante é o input: texto livre, caminho de arquivo ou URL.

## Passo 2 — Garantir um plano APROVADO

1. Se o input é um caminho para um plano com `**Status:** APROVADO` (ou um plano aprovado **nesta sessão** via refine/plan mode) → use-o.
2. Caso contrário (texto, URL, plano DRAFT, ou nada) → **invoque a skill `refine`** (Skill tool) com o input. O refine entrevista se necessário, decide deep-plan vs direto e termina com a aprovação final do usuário — essa aprovação vale como a confirmação para implementar; não pergunte de novo.
3. Se o refine terminar em Cancelar, pare.

Extraia do plano: caminho, branch sugerida, domínios, tier de risco, e o caminho do contrato standalone do deep-plan (`.claude/deep-plan/<branch>-<shortSha>.md`), se existir.

## Passo 3 — Preflight

Execute e **pare com diagnóstico claro** se algo falhar (não improvise):

1. **Working tree limpa**: `git status --porcelain` vazio. Se houver mudanças não commitadas, pergunte ao usuário (stash / commitar / abortar) — nunca descarte.
2. **Branch**: se está na `main`, crie a branch sugerida pelo plano (`git checkout -b <branch>`). Se já está numa feature branch diferente da sugerida, confirme com o usuário qual usar. Registre o nome final — todos os agentes do workflow validam contra ele.
3. **Base atualizada**: `git fetch origin main`.
4. **Docker**: `docker info` (testes usam TestContainers; o daemon é Colima — se estiver parado, sugira `colima start` via `!` e aguarde).
5. **Ledger**: derive `slug` = branch com `/`→`-`; ledger em `~/.claude/implement/<slug>/ledger.md` (crie o diretório). Se o usuário deu **diretivas de execução** (restrições, "em caso de X, faça Y", avisos de armadilha — ex.: "ambiguidade de dinheiro → blocked, não decisão"), semeie o ledger agora com uma seção `## Diretivas (do usuário)` contendo-as: é o canal de injeção de contexto para dentro do workflow, e os agentes as tratam com **precedência sobre decisões autônomas**. Trabalho já feito fora do workflow (ex.: uma "Onda 0" manual) também entra aqui, marcado como concluído com os commits. Se já existir um ledger com ondas concluídas para essa branch, é uma **retomada**: o workflow continua das ondas pendentes, preservando diretivas existentes.

## Passo 4 — Disparar o workflow

Chame `Workflow` com `scriptPath: /Users/rodrigooliveira/.claude/workflows/implement.js` e `args` (objeto JSON real, não string):

```json
{
  "planPath": "<caminho do plano aprovado>",
  "branch": "<branch>",
  "baseBranch": "main",
  "repoRoot": "<git rev-parse --show-toplevel>",
  "ledgerPath": "~/.claude/implement/<slug>/ledger.md (expandido)",
  "timestamp": "<date +%Y-%m-%dT%H-%M>",
  "deepPlanContractPath": "<caminho ou null>",
  "prTitleHint": "<tipo(escopo): descrição em pt-br>",
  "maxWaves": 8
}
```

O workflow roda em background; aguarde a `<task-notification>`. Acompanhe via `/workflows` se o usuário pedir.

## Passo 5 — Pós-workflow

Leia o resultado e reporte ao usuário **liderando com o outcome**:

- `status: "pr-opened"` → URL do PR, ondas executadas, commits, e a seção **Decisões tomadas autonomamente** (cada ponto onde um input de usuário teria sido pedido: opções consideradas + caminho escolhido + porquê — também presente na descrição do PR para o usuário revisar e pedir alterações).
- `status: "blocked" | "verify-failed" | "blocked-gate"` → o que foi commitado/pushado até aqui, a onda/etapa travada e o motivo. **Não** encadeie o review. Se for `blocked-gate` (hook do deep-plan barrou o `gh pr create`), o caminho é completar o plan-contract — nunca instrua o token de override.

Se `status: "pr-opened"` e **não** `NO_REVIEW` → **invoque a skill `review-fix-loop`** (Skill tool) com o número do PR. Ao final dela, consolide o relatório dos dois estágios numa única mensagem final.

## Contrato do workflow (o que `implement.js` garante)

- **Setup**: valida a branch, semeia/retoma o ledger, divide o plano em ≤`maxWaves` ondas (por fase do plano ou por grupos lógicos de commit, per git-conventions), e commita o contrato do deep-plan em `.claude/deep-plan/` quando existir (é o artefato que o hook de PR em branch money lê).
- **Implement**: uma onda por vez, agente fresco por onda, com retry único em caso de `blocked`. Cada onda: implementa só seu escopo → roda verify incremental (spotless, detekt, testes direcionados + ArchitectureTests dos módulos tocados) → commita (Conventional Commits pt-br) → push na branch → atualiza ledger com progresso e decisões. **Gate de fechamento**: a onda não fecha com contract item sem teste nomeado (ou justificativa explícita) nem com premissa nova em `Tests: none yet` — no PR #1065, metade dos Highs do review eram "untested X" que este gate teria pego na origem. **Dimension-row-on-mint**: quantia monetária derivada que o plano não especifica ganha dimension row retroativa no contrato + premissa testada, no mesmo commit.
- **Verify**: `/verify` completo (inclui `clean build`) com loop de fix (≤3 tentativas), depois reconciliação `verify-plan` (Missing/Diverged/Unplanned/UntestedPremises vs Contract — o 4º bucket é o grep mecânico por `Tests: none yet` nas premissas da branch) com 1 rodada de fix; residuais viram seção explícita do PR, nunca silêncio.
- **PR**: rebase sobre `origin/main` (re-verifica se o rebase trouxe mudanças), push, e `gh pr create` com corpo extenso em pt-br seguindo `.claude/rules/git-conventions.md` — Resumo, Plano de teste, Decisões tomadas autonomamente, e seções condicionais (payloads, rollback, tabelas) quando aplicáveis.
- **Decisões em vez de perguntas**: agentes de workflow não têm `AskUserQuestion`. Em qualquer ponto de decisão, o agente registra as opções, escolhe a que melhor serve o plano, e segue — o registro aparece no ledger, no output do workflow e na descrição do PR.

This should work for desktop and web.

Base directory for this skill: /Users/rodrigooliveira/.claude/skills/refine

`refine` é a etapa de planejamento do pipeline `refine → implement → review-fix-loop`, mas funciona isoladamente. Ela recebe uma intenção em qualquer formato, resolve o conteúdo, decide se precisa entrevistar o usuário, escreve um plano com os artefatos de `.claude/rules/planning.md`, **decide sozinha** se o risco justifica rodar `/deep-plan`, e só então volta ao usuário para a aprovação final. O output é um arquivo de plano carimbado como APROVADO — exatamente o input que `/implement` consome.

Este skill roda **inline na conversa principal** (precisa de `AskUserQuestion`); ele não dispara Workflow diretamente — no máximo invoca `/deep-plan`, que tem seu próprio Workflow.

---

## Fase 0 — Resolver o input

Classifique o argumento e materialize a **intenção bruta** (brief):

1. **Caminho de arquivo existente** → leia. Se já for um plano com `## Contract`, trate como rascunho a refinar (não como brief cru).
2. **URL** — resolva pelo host:
   - `github.com/.../issues/N` → `gh issue view N --repo <owner/repo> --json title,body,comments`
   - `github.com/.../pull/N` → `gh pr view N --repo <owner/repo> --json title,body,comments`
   - Jira (`*.atlassian.net/browse/KEY-N`) → ToolSearch `+atlassian` e use as tools do MCP Atlassian (autentique se necessário via `authenticate`).
   - Slack (`.../archives/<channel>/p<ts>`) → ToolSearch `+slack read thread` e use `slack_read_thread`.
   - Google Drive/Docs → ToolSearch `+drive read` e leia o conteúdo.
   - Outra URL → ToolSearch `select:WebFetch` e busque.
3. **Texto livre** → é o próprio brief.

Eco do brief: resuma em 2–4 linhas o que entendeu que deve ser implementado e **de onde veio** (link/arquivo). Se o brief vier vazio ou a URL não resolver, pare e pergunte.

## Fase 1 — Contexto do codebase

Igual ao Phase 1 do deep-plan, mas mais leve:

1. Liste os **domínios afetados** a partir do brief. Para cada um, leia `docs/{domain}/premises.md` e `docs/schema/{domain}.md` (se existirem) e `docs/CORE_TENETS.md`.
2. Despache 1–3 agentes **Explore** em paralelo para mapear os arquivos/serviços/fluxos que a mudança toca (breadth "medium"; "very thorough" se o brief for vago sobre onde mexer). Você quer: pontos de wiring, guards existentes, callers, testes que cobrem o fluxo hoje.
3. `rg`, nunca `grep -r` (escopo do repo, ignora worktrees/build).

## Fase 2 — Entrevistar ou não (julgamento)

Entreviste **apenas se** existir ambiguidade material: múltiplas interpretações razoáveis do escopo, invariante não declarada da qual a implementação dependerá, edge case com respostas plausíveis divergentes, ou tradeoff que muda a arquitetura (ex.: síncrono vs outbox). Use `AskUserQuestion` (até 4 perguntas por rodada, máx. ~2 rodadas — siga o roteiro de entrevista de `.claude/rules/premises.md`: "que invariantes existentes essa mudança assume?", "o que quebra em outro lugar se a premissa for falsa?").

Para todo cenário que o plano decide **deferir** ("fora de escopo", "tratamos depois"), acrescente a pergunta: **"com que frequência o caso deferido dispara em produção?"** Gatilho rotineiro será re-litigado no review como se fosse gap (caso clawback do PR #1065: deferido no plano, re-aberto em review porque o gatilho era rotineiro) — ou o plano o trata, ou a justificativa do deferral entra na prosa com o dado de frequência.

Se o brief é inequívoco, **diga isso em uma linha e siga** — não fabrique perguntas. O paradoxo da autocrítica do deep-plan vale aqui: cerimônia em tarefa simples ensina o usuário a ignorar o skill.

## Fase 3 — Autorar o plano

Escreva o plano seguindo `.claude/rules/planning.md` e `docs/planning/plan-contract.md`:

- **Prosa**: contexto, abordagem escolhida (e alternativas descartadas, com 1 linha de porquê), fases de implementação se multi-fase.
- **`## Contract`** (sempre): lista numerada de compromissos atômicos verificáveis.
- **Interaction matrix** e **Precondition diff**: quando os gatilhos do plan-contract se aplicarem (status/lifecycle novo, state machine, registro RESERVED/PENDING longevo; método/fluxo deletado/substituído ou guard copiado).
- **Cabeçalho de metadados** no topo do arquivo:

```markdown
# {título}

**Origem:** {texto | arquivo | URL resolvida}
**Branch sugerida:** {tipo}/{slug-kebab}   ← siga .claude/rules/git-conventions.md
**Domínios:** {lista}
**Tier de risco:** {direto | deep-plan} — {1 linha de justificativa}
**Status:** DRAFT
```

Salve em `~/.claude/plans/<slug-kebab>.md`. (É o diretório que `/verify-plan` e o hook `deep-plan-pr-gate.sh` escaneiam.) Se o plan mode da sessão bloquear o Write, apresente o plano na conversa e escreva o arquivo logo após a aprovação da Fase 6.

## Fase 4 — Ilustrar outcomes críticos (julgamento)

Se o plano produz outcomes cuja forma concreta o usuário precisa validar — payload de API/evento novo ou alterado, fluxo de dinheiro (quem recebe quanto em que conta), antes/depois de uma mutação de dados, schema novo — **mostre o exemplo concreto** (JSON realista, tabela antes/depois, conta aritmética em centavos) e confirme com `AskUserQuestion`. Pule quando o outcome é óbvio pelo próprio contrato (refactor sem mudança de comportamento, fix pontual).

## Fase 5 — Tier de risco: deep-plan ou direto (decisão autônoma)

Decida **sozinha** — não pergunte — e declare a decisão com justificativa de 1–2 linhas. Rode `/deep-plan` (via Skill tool, passando o caminho do plano como intent file) quando **qualquer** um valer:

1. **Regra do deep-plan Phase 0**: domínio money (`paymentgateway`, `storecredit`, `billing`, `debtsettlement`, `cohort`, `payout`, `notary`) **e** a mudança adiciona/modifica status/lifecycle de entidade, introduz state machine, cria registro RESERVED/PENDING longevo, ou substitui fluxo/método existente.
2. **Likelihood de bug high/crítico** por outros vetores: ordering assíncrono novo (listener/outbox/webhook), concorrência/locking, migration com backfill de dados money, refactor que cruza ≥3 módulos/domínios, ou mudança em cálculo monetário (rounding, rateio, caps).

Caso contrário, siga direto. Em dúvida genuína entre tiers em domínio money, prefira deep-plan (false-heavy é barato; false-light embarca o gap).

Quando o deep-plan rodar: use a opção "Write artifacts into the plan" dele para fundir o contrato refutado no arquivo do plano, e **anote no cabeçalho** `**Tier de risco:** deep-plan (rodado — contrato fundido)`. GAPs residuais viram itens explícitos da aprovação na Fase 6, nunca silenciosamente aceitos. O contrato standalone que o deep-plan grava em `.claude/deep-plan/<branch>-<shortSha>.md` será commitado pela wave 1 do `/implement` (é o que o hook de PR lê).

## Fase 6 — Aprovação final (sempre)

Independente do tier, **volte ao usuário** com `AskUserQuestion`:

- Resumo do plano em ≤10 linhas: o que muda, contract size, tier de risco, GAPs residuais do deep-plan (se houver), branch sugerida.
- Opções: **Aprovar** / **Ajustar** (colete o ajuste, volte à Fase 3) / **Cancelar**.

Na aprovação, atualize o cabeçalho para `**Status:** APROVADO — refine {data}` e termine reportando:

```
Plano aprovado: ~/.claude/plans/<slug>.md
Branch sugerida: feat/<slug>
Próximo passo: /implement ~/.claude/plans/<slug>.md
```

Quando invocada **pelo `/implement`**, a aprovação daqui já vale como a confirmação final — o implement não pergunta de novo.

## Regras

- **Enumere do codebase, não da memória** — wiring points e guards no Contract vêm de grep/Explore, não de recall.
- **Não escolha silenciosamente entre alternativas** — interpretações concorrentes vão para a entrevista (Fase 2) ou aparecem como alternativa descartada na prosa.
- **Plano mínimo que resolve** — nada especulativo no contrato; cada item rastreia ao brief.
- **Tier honesto** — não rode deep-plan em typo fix; não light-passe lifecycle money.
